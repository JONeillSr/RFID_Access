Bringing up a new board

Worked example: ESP32-S31
RFID_Access · firmware 2.6.0
Fleet jtc-prod-rfidaccess-eastus2

The order of these steps is not convenience, it is recoverability. Everything above the gate is undoable with a USB cable on your bench. Everything below it lands on doors that may be in someone else's building.

Status of this part, checked against the installed toolchain pio boards returns no definition matching “s31”, so stage 1 currently fails and nothing downstream can proceed. Flash size, core architecture and pin map are therefore still unknown — they are outputs of stages 1–3, not assumptions to carry in. Fill them in as you go.
Bench — every step here is undoable with a cable
  1. 1

    Toolchain support

    Without a board definition you cannot build at all. platform tracks pioarduino's rolling stable zip, so an update may be all it takes.

    pio pkg update
pio boards | findstr /i "s31"
    Gate The part appears with its flash size. If it does not, stop: either wait for platform support or author a custom board JSON under boards\. Nothing below is worth doing first.
  2. 2

    Memory map

    partitions_rfid.csv is a 4 MB table with app0/app1 = 0x1D0000. Record what this part actually has.

    # flash column from the board listing
pio boards espressif32 | findstr /i "s31"
    Gate Flash is at least 4 MB. More is fine — the table simply leaves the rest unused, as it already does on the 8 MB S3. Less, and this table cannot be used. The OTA slot is a hard wall: publish-fw refuses any image larger than it. Never move nvs.
  3. 3

    Define the board

    Two files. The pin map is the part that matters; everything else compiles already.

    lib\BoardConfig\BoardConfig.h   BOARD_ESP32S31 block: BOARD_NAME + pins
platformio.ini                  [env:esp32s31], board =, -D BOARD_ESP32S31
    Gate Every pin metered against the actual wiring: reader clock and data, relay, exit button, OLED SDA/SCL, status LEDs. Do not trust a map copied from a neighbouring part.
  4. 4

    Build

    cd C:\PlatformIO\Projects\RFID_Access
pio run -e esp32s31
    Gate [SUCCESS], zero warnings, and flash use comfortably inside the OTA slot. The four existing boards sit near 73%.
  5. 5

    Flash over USB and prove it

    The whole purpose of the bench stage. A board that has never run from a cable must never be offered over the air.

    pio run -e esp32s31 -t upload
pio device monitor -e esp32s31
curl http://<device-ip>/status.txt
    Gate Board: correct · OLED: OK · reader decodes a real fob · filesystem mounted · Heap minimum clear of 45 KB · relay fires and re-locks. On a new core, also confirm the reader ISRs landed in IRAM — dropped edges only under WiFi load is that bug's signature.
Point of
no return
Publishing puts this image in front of every door reporting that board. A bad OTA image does not misbehave — it fails to boot, and the door is dead until somebody reaches it with a cable. Do not cross on a build that has not run on real hardware.
Fleet — reaches doors you may not be able to reach
  1. 6

    Publish

    Run from cloud\api; npm does not search upward, so this fails in any other folder.

    cd cloud\api
$env:STORAGE_ACCOUNT_NAME = "jtcprodrfidaccessst"

npm run publish-fw -- --board "ESP32-S31" --version 2.6.0 `
   --file ..\..\.pio\build\esp32s31\firmware.bin

npm run publish-fw -- --list
    Gate The tool prints image self-reports 2.6.0 — matches, and --list shows the board string spelled exactly as the device reports it on /status.
  2. 7

    Pair and confirm

    Pairing code from the Doors page, entered on the device's /setup. The unit you flashed is already current; publishing is what keeps it current and what updates the second one.

    npm run fleet
    Gate The door reports 2.6.0, is checking in, shows up to date. Set fwHold on any door you cannot easily reach until the first has proven the image in service.
Three ways to strand a door
01
A misspelled board string The publish succeeds. Doors of that board are then offered nothing, forever, and nothing anywhere reports a problem. Copy it from BoardConfig.h or the door's own /status.
02
A version the image does not report Every door on that board flashes, reboots, still reports the old version, is offered the new one again — permanently. The device cannot detect it. The tool reads the marker back and refuses; do not force past it.
03
Publishing firmware.factory.bin That is the merged image for USB flashing at offset 0. In an OTA slot it produces a device that will not boot. The tool refuses it — this is why.

Rolling back means publishing the previous image again — the backend offers whenever the published version differs, not only when it is newer. Keep the last known-good .bin outside .pio\: a rebuild overwrites it, and you cannot roll back to a file you no longer have.

Publish only for boards you actually run — an untested image waiting for the first door of its type to pair is a trap, not a convenience. JT Custom Trailers
